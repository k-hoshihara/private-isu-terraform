# tutorial-review — チュートリアルレビュー

## 使い方

1. 対象ファイルを通読する（コードブロックの中身を含む）。
2. 下の観点で検査し、指摘を出す。問題なければ「指摘なし」と明言する。
3. 指摘があれば修正し、修正箇所を再検査する。指摘が無くなるまで繰り返す。
4. ループ終了条件: ブロッカー 0 件。残件があるまま終わらない。

## 検査観点

### A. サーバを壊さないか（ブロッカー）

- `upstream` が `server` ブロックの中に無いか。http コンテキストか。
- `nginx -t` の前に reload / restart していないか。`.orig` の退避があるか。
- unit 本体を直接編集していないか。drop-in に `ExecStart=` の空行があるか。`daemon-reload` があるか。
- symlink（`sites-enabled/isucon.conf`）を置き換える手順で、その旨の注意があるか。
- `pip install` に `--break-system-packages` があるか（Ubuntu 24.04）。
- 生成スクリプトに土台ファイルの存在確認があるか（空上書きしないか）。
- slow log を `truncate` していないか。`long_query_time=0` を戻しているか。
- 存在しないファイルを `mv` していないか（guard があるか）。

### B. 順序は正しいか（ブロッカー）

- 使うもの（変数・ファイル・サービス・ツール）がその手順より前で用意されているか。
- 再起動・反映の前に設定が置かれているか。ベンチの前に疎通確認があるか。
- 前のチュートリアルの変更と干渉しないか（例: 0040 §6 の `Cache-Control` が残ったまま 0070 に入っていないか）。
- 前提に書いた状態と手順の最初が一致しているか。

### C. 正本と合っているか（ブロッカー）

`tutorial-author` SKILL の「0. 正本の確認」の表と突き合わせる。パス・ファイル名・既定値・unit の `ExecStart`・フラグ類（`-u memcache` など）が `backup/base/` と違うものは指摘する。`backup/base/` に無い前提（ツールの有無など）は前提節に書かれているか見る。

### D. Python 専用か（ブロッカー）

- Go 言語の使用（コード・`go build`・Go 用設定・Go 前提の説明）が残っていないか。
- 他言語 unit の `disable`・一覧表示は残してよい（ポート競合防止のため）。ただし「Go で試す」等の誘導文は消す。
- `webapp-setup/go.md` へのリンクが残っていないか。

### E. 方向性どおりか（警告。ただし繰り返しはブロッカー扱い）

- タイトルが内容を表しているか（「1台ドリル」のような意味不明な名前は不可）。
- 手順に不要な「前提:」の箇条書きが無いか（削れる情報は削る）。
- `backup/base` を変更する手順が無いか（基準線は不変）。
- 変更先が `backup/s1`・`s2`・`s3` になっているか（`$REPO直下/s*` や `common/` 直下などの迷子が無いか）。
- feature ブランチでやり取りしているか（main 直 push が無いか）。
- サーバ直編集に戻っていないか（作業機で作る → push → pull → `cp` → 反映）。
- 前提と出口が書かれているか（0010→0090 の鎖が切れていないか）。
- ベンチが最低 1 回あるか。ベンチ時刻にフルコマンドが書かれているか（参照のみは不可）。
- 補足が `?>` 形式か。

### F. 日本語の水準（警告）

- 述語欠落の体言止めが無いか。
- スラング・造語が無いか（殴る、当たり、即死、両建て、素叩き、2 数、こっち、ディストリ、軽重、同時入れ、本番適用、旨）。
- 番号参照が文書名付きか（「0030 の〜」は不可）。
- 手順の箇条書きに「確認すること」があるか。

## 指摘の形式

```text
[ブロッカー] file:line — 内容。直し方。
[警告] file:line — 内容。直し方。
```

行番号は `grep -n` で確認したものを書く。推測の行番号は書かない。

## 再検査の規則

- 修正後は指摘箇所の前後を通読し直す（1 行だけ見ない）。
- 同じ観点を全ファイルに再適用する（1 ファイルの指摘は他ファイルにもある前提で探す）。
- 新たな指摘が出たら同じループに入れる。

### G. 用語・構成（警告。ただし繰り返しはブロッカー扱い）

- 用語は初出で定義する。`正本` のような意味不明な語は `投稿の本体データ` のように具体化する。未定義のまま使う造語は不可。
- 情報のない節を置かない。各節に手順・コマンド・判定のいずれかがあること（空の「ベースライン」節などは削る）。
- 初出のツールは install 手順を網羅する（apt / バイナリ / pip の完全な導入手順がそのチュートリアルに書かれているか）。
- 内容がその番号・段階にふさわしいか。早すぎる内容（序盤での設定ノブ回しなど）は後の番号のチュートリアルに移す。
- 手順書レベルか。各手順にコマンド全文・期待出力・成功の見え方があること。「〜を見よ」だけの参照、ベンチ時刻のコマンド省略は不可。
- 文書内・文書間のアンカーが実在する節を指しているか（ファイル分割・節移動のたびに全リンクを確認する）。

## 1. app-3 の余剰 CPU にアプリを置く（不採用）

[0170](../valid/0170-mysql-host.md) で app-3 を DB 専用にしました。**DB は 1 ms 以下で返している**ので CPU に余裕がありそうです。そこに**アプリを 2 worker だけ**置いてみました（6 worker ではなく、DB を圧迫しないつもりで）。

```bash
# app-3 で
sudo sed -i 's|^workers = .*|workers = 2|' /home/isucon/webapp/python/gunicorn.conf.py
sudo systemctl enable --now isuride-python.service
```

| 構成 | 1 本目 | 2 本目 | 3 本目 | いちばん悪い回 |
| --- | --- | --- | --- | --- |
| 0200 の後（app-3 = DB 専用） | 21719 | 20366 | — | 20366 |
| **app-3 に 2 worker 追加** | 12089 | 15646 | **8043** | **8043** |

**負けです。**`2 worker` でも、**DB と同じコアを奪う**とここまで落ちます。**0170 の「DB は専用」が、worker 2 つでも崩れる**ことの実証になりました。

```bash
# 戻す
sudo systemctl disable --now isuride-python.service
```

## 2. 残りの案をやらなかった理由

| 案 | 判断 |
| --- | --- |
| `chair/coordinate` の `chair_locations` 読み直しを消す | **1 往復は減るが `recorded_at` が変わる**。ベンチの検証に触るリスクに対して、`INSERT` 1 回ぶんの往復は小さい。**測る前に対象から外した** |
| アプリの 1 リクエストあたりのクエリを 5 → 3 に | `users FOR SHARE` は [0190](../valid/0190-split-app.md) で削除済み。**残りは `rides` と `chairs` の 1 行読み**で、**DB は 1 ms 以下**。削っても効かない |
| `pymysql` → C ドライバ | Python 3.13 で**ビルドできない**（[0150](../valid/0150-mw-lib.md)） |
| `owner/chairs` / `owner/sales` の N+1 | `owner` 系は **AVG 0.36 s**（ほかの 3 倍）で、**椅子ごとに 1 クエリ**を回している。**件数が 0.4% なので優先度は低い**（単一の `GROUP BY` にできる） |
| 4 台目を足す | この教材は **3 台**の範囲。`terraform apply` はしない方針 |

?> **「まだ何かあるはず」で手を打たない**のも判断です。**alp でアプリ 0.12 s・DB 1 ms** と分かった時点で、**残りは CPU の量**（app-1 / app-2 の 4 コア）です。**アプリのコードを削っても、この 4 コアは増えません。**

## 2-2. 決済をトランザクションの外に出す（不採用）

評価（`POST /api/app/rides/{ride_id}/evaluation`）は **1 回 2.0〜2.8 秒**かかります。nginx の `$apptime` で見ると**アプリの中**で 2 秒使っていて、原因は**決済の HTTP 呼び出しが `engine.begin()` の中**にあることです。2 秒のあいだ、行ロックと DB 接続を握ります。

```python
# AMI のまま（app_post_ride_evaluation）
with engine.begin() as conn:
    ... rides を更新し、ride_statuses に COMPLETED を入れ ...
    request_payment_gateway_post_payment(...)   # ← ここで 2 秒
```

**外に出して測りました。**

| 構成 | 1 本目 | 2 本目 | `map[30]` |
| --- | --- | --- | --- |
| 決済がトランザクションの中（AMI） | 20780 | 19790 | **6〜9 件** |
| **決済を外に出す** | 22861 | 19624 | **60〜118 件** ✗ |

**`map[30]` が 10 倍以上に増えました。**ベンチのログによると、`map[30]` は「**ライドは COMPLETED なのに、決済がまだ**」という不整合です。決済を外に出すと、**完了が先に世界に見えてしまいます**。

?> **2 秒のトランザクションは、遅いのではなく「正しさの単位」**でした。`evaluation` の書き込み・`COMPLETED` の通知・決済を**同じトランザクション**に入れることで、「完了しているなら必ず決済済み」が保証されます。**この教材では戻しました。**

?> **3 台とも c5.xlarge の構成では、この改修が効きました**（35,487 → 41,913 / 40,062）。[0230](0230-scale-up.md) §5-2 を参照。現在は**採用**しています。

?> 順番を逆（**決済 → そのあと DB 書き込み**）にすれば、2 秒のあいだロックを持たずに同じ保証ができます。**ただし「決済したのに書き込みに失敗した」ときの再試行**（`Idempotency-Key` で同じ決済に戻る）を詰める必要があり、**測っていません**。次に挑むならここです。

?> 途中で `response = ...` を `except` の中に入れてしまい、**500 を返してベンチが停止**しました（`CODE=5` / `CODE=12`）。**インデントを変えるパッチは、`import` と 1 本のベンチで必ず確かめます**。

### 2-3. 決済 → 書き込み の順に入れ替え（不採用）

前節の失敗は「**書き込みが先、決済が後**」だったからです。順番を逆にして、**決済 → 短い書き込みトランザクション**にしました。決済は接続もロックも持たない場所で行い、そのあとで `evaluation`・`COMPLETED`・椅子の成績を 1 つの短いトランザクションで書きます。

| 構成 | 1 本目 | 2 本目 | 3 本目 | 4 本目 | `map[30]` |
| --- | --- | --- | --- | --- | --- |
| 決済がトランザクションの中（AMI） | 20780 | 19790 | — | — | 6〜9 件 |
| **決済 → 書き込み** | 22002 | 22512 | 22709 | **15760** | **7〜12 件**（増えない） |

**`map[30]` は増えませんでした**（前節の 60〜118 件とは別物）。狙いどおり「完了しているなら必ず決済済み」は保たれ、行ロックも減りました（1 窓 **1,516 ms**）。

?> **それでも採用しませんでした。**決済（2 秒）のあとに書き込みが失敗すると、**「決済したのに完了していない」**が残ります。`Idempotency-Key` で同じ決済に戻れるので再試行で直りますが、**スコアも上振れしなかった**（平均 20,285 → 20,746、いちばん悪い回 19,790 → 15,760）ので、**シンプルな AMI の順序を残しました**。

?> **`map[30]` の正体も分かりました。**ベンチのログでは「**取得した付近の椅子情報に不備があります**」（105 件）と「**ID:... の椅子は既にライド中です**」でした。**`nearby-chairs` が返した直後に、マッチングがその椅子を別のライドへ割り当てる競合**です。AMI にも 1〜2 件あり、**マッチングを速くしたぶん増えます**。決済とは無関係でした。

?> **時間帯でスコアが落ちます。**同じ構成で 12:05 は **25,349**、15:14 は **14,453** でした。**長く回した環境では、まず再起動や作り直しを疑う**（[0210](../valid/0210-result.md) §5 の判断ルール）。

### 2-4. owner 系の N+1 を 1 クエリに（採用）

`owner_get_sales` は**椅子ごとに 1 クエリ**（`rides JOIN ride_statuses`）を回していました。owner の椅子ぶんを**1 回のクエリ**で取り、Python 側で椅子に振り分けます。

| 構成 | 1 本目 | 2 本目 | `owner/sales` のクエリ |
| --- | --- | --- | --- |
| 椅子ごとに 1 クエリ | 21363 | 19368 | 椅子数ぶん |
| **1 クエリに** | **23177** | 14679 | **1 回**（digest から消えた） |

スコアは帯の中ですが、**クエリ数が椅子数に比例しなくなりました**（[0080](../valid/0080-sql-n1.md) と同じ手）。

### 2-5. gunicorn の worker 数（4 / 6 / 8）

| workers | 1 本目 | 2 本目 | いちばん悪い回 | ばらつき |
| --- | --- | --- | --- | --- |
| 6（それまで） | 21363 | 19368 | 14161 | **大** |
| **4** | **24376** | **24530** | **24376** | **154** |
| 8 | 23606 | 24023 | 23606 | 417 |

**4 が最良で、いちばん安定**していました。2 vCPU に 6〜8 worker を載せると **CPU の取り合い**になり、リクエストごとの待ちが増えてスコアが振れます。**worker は「多いほど良い」ではなく、コア数に合わせます**（4 で確定）。

# 0170 MySQL を専用台に置く

[0160](0160-split.md) で 3 台に分けて **14694** まで来ました。この章は**MySQL をどこに置くか**です。3 台しかないので、**必ずどれかと同居**します。**どこに置くのが正解か**を測って決めます。

## 1. まず「移すだけ」を試しました（失敗）

`app-3` の MySQL を外に開き、3 台のアプリの向き先を `app-3` に変えて測りました。**アプリは app-3 で動かしたまま**です。

| 構成 | 1 本目 | 2 本目 | 3 本目 | いちばん悪い回 |
| --- | --- | --- | --- | --- |
| 0160（DB は app-1） | 14694 | 13064 | 12007 | 12007 |
| **DB を app-3 へ（アプリも app-3）** | **8984** | **9061** | **10869** | **8984** |

**負けました。**理由は単純で、**app-3 ではアプリの 6 worker と MySQL が同じ CPU を奪い合う**からです。worker を 3 に落として MySQL に CPU を渡す形も試しましたが、**9259 / 8703** でさらに悪くなりました（アプリの処理能力が落ちるほうが痛い）。

?> **「DB を別の台に移す」は、その台が DB 専用になって初めて意味があります。**移しただけでアプリも動かしていたら、**ただ 1 台の取り合いが別の台に移っただけ**です。

## 2. 正解: app-3 を DB 専用にします

| 台 | 役割 | 動かすもの |
| --- | --- | --- |
| `app-1` | 入口 + アプリ | nginx、Python 実装（6 worker） |
| `app-2` | アプリ | Python 実装（6 worker） |
| `app-3` | **DB 専用** | **MySQL だけ** |

```bash
# app-3 で
sudo systemctl disable --now isuride-python.service   # アプリを止める（これが本体）
sudo systemctl is-active isuride-python mysql          # inactive / active
```

```bash
# app-1 / app-2 で
sudo sed -i 's|^ISUCON_DB_HOST=.*|ISUCON_DB_HOST="10.0.1.234"|' /home/isucon/env.sh
sudo systemctl restart isuride-python.service
```

?> **`app-1` の MySQL は止めません。**`isuride-python.service` が `Requires=mysql.service` なので、止めるとアプリが起動しません。**使わないまま起動しておきます**（アイドルなので CPU はほぼ食いません）。

?> **`initialize` は app-1 / app-2 のどちらに来ても大丈夫**です。`init.sh` は `ISUCON_DB_HOST` の DB を初期化します（[0160](0160-split.md) §4）。

## 3. 実測（2026-10-20）

| 構成 | 1 本目 | 2 本目 | 3 本目 | いちばん悪い回 |
| --- | --- | --- | --- | --- |
| 0160 | 14694 | 13064 | 12007 | 12007 |
| **app-3 = DB 専用** | 12122 | **21558** | 16258 | 12122 |
| （続けて 2 本） | 13926 | **21819** | — | 13926 |

**最高 21819**（0160 の 14694 から **+48%**）。**平均は 17,000 前後**まで上がりました。

?> **切り替えた直後の 1 本目（12122）は低めです。**アプリを再起動した直後は、**DB のバッファプールが冷えていて**、ウォームアップに 1 本使います。**判断は 2 本目以降の中央値で見る**のが安全です（それでも「いちばん悪い回」で比べる原則は変えません）。

## 4. いちばん大事な発見: SQL は遅くなかった

**同じ SQL の 1 回あたりの時間**を、DB 専用の前後で比べます（`performance_schema` の digest）。

| SQL | 0160（DB は app-1、アプリと同居） | **0170（DB 専用）** | |
| --- | --- | --- | --- |
| `COMMIT` | 30.84 ms | **0.51 ms** | **1/60** |
| 通知の状態読み（アプリ側） | 28.03 ms | **0.39 ms** | **1/72** |
| 通知の状態読み（椅子側） | 31.82 ms | **0.39 ms** | **1/82** |
| `SELECT * FROM rides WHERE chair_id = ? ...` | 8.47 ms | **0.19 ms** | **1/45** |
| `SELECT status FROM ride_statuses ... LIMIT 1` | 24.75 ms | **0.21 ms** | **1/118** |

**SQL は 1 文字も変えていません。**それで **1 回あたりが 45〜118 分の 1** になりました。**「SQL が遅い」の正体は、DB がアプリと CPU を奪い合っていたこと**でした。

?> これは [0150](0150-mw-lib.md) の負荷試験（`iowait` 0.4%・CPU 87.9%）とも一致します。**ディスクでもクエリでもなく、CPU の取り合い**だったわけです。**インデックスを増やす前に、DB に CPU を渡す**——この章の結論です。

## 5. 戻すには

```bash
# app-3 で
sudo systemctl enable --now isuride-python.service
# app-1 / app-2 で
sudo sed -i 's|^ISUCON_DB_HOST=.*|ISUCON_DB_HOST="10.0.1.240"|' /home/isucon/env.sh
sudo systemctl restart isuride-python.service
```

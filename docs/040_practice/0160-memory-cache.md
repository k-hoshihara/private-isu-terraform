# 0160 メモリに逃がす（読み込みのキャッシュ）

?> リポジトリを触る操作（`git pull` / 編集 / `git push`）は、手元の private-isu-terraform リポジトリで実行します。

- [0150-scale.md](0150-scale.md) で機械の割り当てを整えたあと、**読み取りの残りをプロセス内のメモリに逃がします**。
- DB へ行かなくなった分だけ、速くなります。
- ただし、この章には 2 つの罠があります。

1. **覚えさせる量に上限を持たせないと、メモリを使い切り、強制終了（OOM）を出します**（`fail` の原因になります）
2. **点数が良くても `fail` が出るようなら残しません**（ベンチの初期化とぶつかることがあります）

- 「効果が出たか」だけでなく、「**`fail=0` が繰り返し出るか**」で、残すか戻すかを決めます。
- ここが、このチュートリアルの最後の章です。
- ベンチは [0150-scale.md](0150-scale.md) と同じです（ベンチマーカー専用機から、s1 の URL へ）。

- 順番: 仕事量を数える（1.）→ ユーザー情報をメモリに（2.）→ 投稿詳細をキャッシュする（3.）→ 一覧をキャッシュする（4.）→ 判定する（5.）。

```bash
mkdir -p ~/bench-notes
echo "$(date -Iseconds)  score=  pass=  fail=  note=cache-baseline" >> ~/bench-notes/scores.txt
```

<a id="1-仕事量を数える"></a>

## 1. 仕事量を数える

- [0120-db-load.md §1](0120-db-load.md#1-仕事量を数える) と同じ全件キャプチャ（速い問い合わせも全部記録する取り方）で、読み取りの残りを数えます。

実測サンプル（2026-10-13、`c7a.large` 2 台 + s3 `c7a.xlarge` + ベンチマーカー `c7a.xlarge` / `ap-northeast-1`）: ベンチ 1 本で **150,576 クエリ**、`fail=0` の点数は `score=338479`。上位はこうでした:

| クエリ | 件数 | 合計時間 | 見立て |
| --- | --- | --- | --- |
| `INSERT posts` / `users` / `comments` | 759 / 2258 / 1801 | 42 秒 | 書き込み（ここは仕方なし） |
| `SELECT posts WHERE id = N` | **30,225** | 10.2 秒 | **詳細ページの読み** |
| `SELECT comments ...` | 19,358 | 8.4 秒 | 詳細・一覧のコメント |
| `SELECT users WHERE id = N` | **34,575** | 4.0 秒 | **ユーザーの読み** |
| `SELECT posts users`（一覧） | 12,335 | 1.9 秒 | 0120 で詰めた済み |

- 読み取りの **8.4 万件**が、残っています。
- ここをメモリに逃がすのが、この章です。

### 観察すること

- 「回数が多いが 1 回が軽い」問い合わせが、メモリキャッシュの効く相手です
- 書き込み（`INSERT`）はキャッシュできません。消せない残りと分けて言えます

<a id="2-ユーザー情報をメモリに"></a>

## 2. ユーザー情報をメモリに

- `users` は 1000 人程度で、読みが 3.5 万回です。
- **ID と行の組をプロセスに覚えさせ、無い ID だけ DB へ行きます。**
- 見えなくする（無効化する）場所は、2 箇所です（管理画面での利用停止と、ベンチの初期化）。

```python
def _cache_put(cache, key, value, limit):
    """上限付きで入れる。上限を超えたら古いものから捨てる（メモリを食い切らないため）。"""
    cache[key] = value
    while len(cache) > limit:
        cache.pop(next(iter(cache)))


def _get_users(user_ids):
    """id ごとのユーザー行を返す。メモリに無い id だけ DB へ行く。"""
    missing = [uid for uid in user_ids if uid not in _user_cache]
    if missing:
        cur = db().cursor()
        marks = ",".join(["%s"] * len(missing))
        cur.execute(
            "SELECT `id`, `account_name`, `authority`, `del_flg`, `created_at` "
            f"FROM `users` WHERE `id` IN ({marks})",
            missing,
        )
        for row in cur:
            _cache_put(_user_cache, row["id"], row, 2000)
    return {uid: _user_cache[uid] for uid in user_ids if uid in _user_cache}
```

- **上限（`limit`）は、最初から付けます。**
- 無いと、[§3](#3-投稿詳細をキャッシュする) の事故になります。
- `make_posts()` のまとまりごとのユーザー取得を、`_get_users()` に置き換えます（[0120-db-load.md §6](0120-db-load.md#6-残った上位から-1-つ) で入れた `get_session_user()` のキャッシュと同じ `_user_cache` を使います）。

```bash
# s1 と s2 に反映 → restart → ベンチ（ベンチマーカー専用機から）
echo "$(date -Iseconds)  score=  pass=  fail=  note=cache-usercache" >> ~/bench-notes/scores.txt
```

実測サンプル（2026-10-13）: `{"pass":true,"score":347666,"success":328777,"fail":0,"messages":[]}`（基準 338479 から **+9,187**、`fail=0`）。**この手は残します。**

### 観察すること

- 見えなくする場所（利用停止・初期化）を全部言えます。抜けると `fail` になります
- 上限は最初からです。あとから付けると事故ります（[§3](#3-投稿詳細をキャッシュする)）

<a id="3-投稿詳細をキャッシュする"></a>

## 3. 投稿詳細をキャッシュする（戻した例）

- 詳細ページ（`GET /posts/<id>`）は、1 投稿ごとに投稿＋全コメントを組み立てます。
- **組み立て結果を ID で覚えて、コメントを書き込んだときに対象の投稿だけ忘れる**と、速くなります。

```python
# 投稿詳細: _cache_put(_post_cache, id, posts, 256)
# コメント挿入: _post_cache.pop(str(post_id), None)
# 初期化・ban: _post_cache.clear()
```

実測サンプル（2026-10-13）: `{"pass":true,"score":352104,"success":333065,"fail":0,"messages":[]}`（+4,438）。**点数は出ましたが、この手は結局戻しました。** 2 つの事故が出たためです。

- **事故 1: 上限が無いと、メモリを使い切ります。**
- 最初に上限を付けずに載せたところ、ベンチ中にメモリを使い切りました。
- `isu-python` が、強制終了（OOM killer）に殺されました（s2 ごと応答しなくなります）。

```text
systemd[1]: isu-python.service: A process of this unit has been killed by the OOM killer.
systemd[1]: Killing process 4693 (gunicorn) with signal SIGKILL.
```

- この回は、`fail=32` です。
- `journalctl -u isu-python.service` で `oom-kill` を探せば、分かります。

- **事故 2: ベンチの初期化とぶつかり、`fail` が出ます。**
- 上限を入れて安定したあとも、2 回に 1 回くらい `fail=20`（`静的ファイルが正しくありません (GET /image/…)`）が出ました。
- 切り分けは、ID の穴で決着します。

```sql
-- s3 で打つ（失敗した ID の前後を見る）
SELECT id FROM posts WHERE id BETWEEN 48850 AND 48900 ORDER BY id;
-- 48850〜48889 が抜けて 48890 以降だけ残る = ベンチの途中初期化が入った
```

- 投稿を作ったあと・画像を確認する前に、ベンチの次の波の初期化（`DELETE FROM posts WHERE id > 10000`）で消えることがあります。
- 消えたものが 500 を返し、「内容が違う」と判定されています。
- キャッシュで応答が速くなって順番が変わると、この取りこぼしに負けやすくなります。

- **判定: 効果が +4,438 でも、`fail=0` を繰り返し出せない手は、残しません。**
- 戻すと、2 本連続で `fail=0`（348683 / 350051）に戻りました。

### 観察すること

- `fail` が出たときは、点数ではなく**切り分けが先**です（[0120 §2](0120-db-load.md#2-画像の整合を取るfail-が出たときの切り分け) も同じ流儀）
- 効果の大きい手でも、安定性で戻すことがあります。理由を書いて残します

<a id="4-一覧をキャッシュする"></a>

## 4. 一覧をキャッシュする（効かない例）

- 一覧（`/`）は、新しい投稿・コメントのたびに変わります。
- **書き込みのたびに古い物を捨てる**形で載せても、効きません。
- ベンチ中に、書き込みが毎秒 40 件近く入ります。キャッシュが生きている時間は、数十ミリ秒です。

実測サンプル（2026-10-13）: `score=352229`（`fail=0`）。[§3](#3-投稿詳細をキャッシュする) の直後 352104 から **+125＝ノイズ内**でした。効果が無いのに表示の順番だけ崩すので、この手も**戻しました**。

### 観察すること

- **忘れさせることが多いキャッシュは効きません。** 「書き込みの頻度」と「読みの頻度」を比べてから載せます
- 効かない手は、載せたままにしないでください（複雑さだけが残ります）

## 6. トラブルシュート

### `fail` が急に出る（キャッシュを入れたあと）

- `journalctl -u isu-python.service` で `oom-kill` を探します（[§3](#3-投稿詳細をキャッシュする)）
- 画像の内容が違うというエラーなら、失敗した ID の前後の穴を見ます（ベンチの初期化との取りこぼし。[§3](#3-投稿詳細をキャッシュする)）

### キャッシュした値が古い

- 見えなくする場所を数え直します（この章では利用停止・初期化・コメント書き込み）。1 箇所抜けると `fail` になります
- 迷ったら**戻します**。キャッシュは「速くなる手段」であって目的ではありません

### メモリが足りない

- 上限を小さくします。キャッシュの目的は 1 回の DB 往復を減らすことで、全部を覚えることではありません
- `free -h` の `available` と、worker 数 × キャッシュ上限の積を見比べます

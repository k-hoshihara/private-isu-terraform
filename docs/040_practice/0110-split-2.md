# 0110 複数台に分割する（中盤:分割実装）

?> リポジトリを触る操作（`git pull` / 編集 / `git push`）は、手元の private-isu-terraform リポジトリで実行します。

- [0110-split-1.md](0110-split-1.md) の続きです。
- 役割を決め、分ける前の基準（ベースライン）を取った状態から、分割の実装（§8）に入ります。

## 8. nginx / アプリ / 静的ファイル / MySQL

- s1（入口）・s2（重いアプリ）・s3（DB）に、役割を分けます。
- 順番は、s3 → env → memcached → s2 → s1 unix → nginx です。
- s1 unix と nginx は、隣同士でやります（間にベンチは挟みません）。

- 流し方（変更の反映の仕方）は、全部同じです。
- **サーバに入って、直接編集しません。**
- 作業機のリポジトリでファイルを作って push し、各台で pull して `cp` で移します。
- やり取りの枝は、`feature/backup` に統一します（`feature/split` には載せません）。
- 作業機のコマンドは、すべてローカル環境の private-isu-terraform リポジトリで実行します。
- 各反映の締めは、restart → s1 からの公式ベンチ 1 本 → `scores.txt` への記録です。
- `fail`（エラーの件数）が 0 でなければ、次に進みません。



### 1. 作業機 — IP を `backup/common/ips.sh` に書く

- [1.](0110-split-1.md#1-起動した-ec2-インスタンスを確認します) で控えたプライベート IP を、ファイルにします。
- シェルの変数に入れるだけでは、消えます。ファイルに書き出します。
- 以降の作業は、このファイルを `source` して使います。

- **下の IP を、自分の値に直してから**配置し、push します。

`backup/common/ips.sh`:

```bash
# s1 のプライベート IP（静的の rsync 用。後で使う）
WEB_PRIV='10.42.0.21'
# s2 のプライベート IP（重いアプリ、HTTP）
APP_PRIV='10.42.0.181'
# 共有 memcached。既定は s2 なので APP_PRIV と同じ
MC_PRIV='10.42.0.181'
# s3 のプライベート IP
DB_PRIV='10.42.0.168'
SOCK='/home/isucon/tmp/gunicorn.sock'

```

```bash
# 作業機
git fetch origin
git switch feature/backup 2>/dev/null || git switch -c feature/backup
git pull --ff-only 2>/dev/null || true
mkdir -p backup/common/
# 上の内容を配置する

git add -A
git commit -m "split: 台の IP を backup/common/ips.sh に置く"
git push -u origin feature/backup
```

- **AMI 側で `backup/common/` が無いことを確認してから、作業します。**
- `gh repo clone` で取るリポジトリの `main` 起点には、`backup/common/` が含まれていません。
- そのまま `cat backup/common/ips.sh` を叩くと、次のようになります。

```text

```

- `mkdir -p backup/common/` を、先に実行してから配置します。
- AMI 側で作業する場合（作業機を使わず各台が直接 push する場合）も、同じです。

```bash

git reset --hard origin/feature/tooka 2>/dev/null || git reset --hard origin/feature/backup

# 上の内容を配置する

git push origin feature/tooka 2>/dev/null || git push origin feature/backup
```

- AMI 側の clone にある remote（送り先）は、`origin` だけです（[0110-split-1.md](0110-split-1.md) §3 を参照）。



### 2. MySQL（s3 だけ）

- **目的:** s1・s2 から、MySQL（s3）に届くようにします。
- 作業機で、設定ファイルを作ります。

`backup/s3/etc/mysql/mysql.conf.d/zz-bind-all.cnf`:

```ini
[mysqld]
bind-address = 0.0.0.0
mysqlx-bind-address = 0.0.0.0
```

`backup/s3/home/grant-split.sql`:

```sql
CREATE USER IF NOT EXISTS 'isuconp'@'10.42.%' IDENTIFIED BY 'isuconp';
GRANT ALL PRIVILEGES ON isuconp.* TO 'isuconp'@'10.42.%';
FLUSH PRIVILEGES;
SELECT user, host FROM mysql.user WHERE user = 'isuconp';
```

```bash
# 作業機
mkdir -p backup/s3/etc/mysql/mysql.conf.d backup/s3/home

# 旧名の 99-bind-all.cnf は消す。同じ名前のファイルが 2 つあると
# 後に読まれた `mysqld.cnf` の bind-address=127.0.0.1 が残ってしまう
rm -f backup/s3/etc/mysql/mysql.conf.d/99-bind-all.cnf
rm -f backup/s3/home/grant-split.sql
# 上の内容を各ファイルに配置する

git add -A && git commit -m "split: s3 の bind-all と GRANT" && git push
```

- VPC CIDR（内部ネットワークの範囲）が `10.42.0.0/16` 以外なら、`grant-split.sql` の `10.42.%` を合わせます。
- 現在の Terraform は、この範囲です。



- s3 で、反映します。

```bash

sudo cp -a "$REPO/backup/s3/etc/mysql/mysql.conf.d/zz-bind-all.cnf" /etc/mysql/mysql.conf.d/

# 0.0.0.0:3306 または *:3306 であることを確認する。これで他サーバからアクセスができるようになる
```

### 3. アプリの env.sh（s1 と s2。同じ内容）

?> アプリのソースは、1 台に全部入った構成で作業した台（s1）の `backup/s1/home/private_isu/` に積んだものが正です。増やした台の `app.py` は、素体（配布された元の状態）のままです。s2 へは、同じ内容を配ります（[0015-sql-tuning.md §7](0015-sql-tuning.md#7-n1-を一括化する) の N+1 一括化などが無ければ、足します。確認は [0110-split-4.md §1](0110-split-4.md#1-分割後の-sql-を確認する) でもやります）。

- Python の初期設定は、DB=`localhost`、memcached=`127.0.0.1:11211` です。
- まず **DB=s3 だけ** に向けます（memcached は、§4 で s2 に向けます）。
- 作業機で設定ファイルを作って、git に反映します。

```bash

source backup/common/ips.sh
# s1, s2のenv.shにISUCONP_DB_HOSTだけ追加する（ISUCONP_MEMCACHED_ADDRESS は §4 で付ける）
# 土台が空だと env.sh を空で上書きするので先に止める
if [ ! -s backup/s1/home/env.sh ]; then
  echo 'backup/s1/home/env.sh missing'
  exit 1
fi


for h in s1 s2; do
  grep -v '^ISUCONP_DB_HOST=\|^ISUCONP_MEMCACHED_ADDRESS=' backup/s1/home/env.sh > /tmp/env.new
  echo "ISUCONP_DB_HOST=${DB_PRIV}" >> /tmp/env.new
  cp /tmp/env.new backup/$h/home/env.sh
done

# env.shを確認する（ISUCONP_MEMCACHED_ADDRESS はまだ無いこと）
cat backup/s1/home/env.sh

cat backup/s2/home/env.sh

git add -A && git commit -m "split: env.sh を DB=s3 に向ける" && git push
```



- s1 と s2 で、反映します（env.sh を移して、s1・s2 の DB を s3 に向ける）。

```bash

## s2の場合はこちら

# s1 と s2 の中身は同じなので、自分の台の行だけ打つ

# cat をし、ISUCONP_DB_HOST が s3 であることを確認する（ISUCONP_MEMCACHED_ADDRESS はまだ無い。§4 で付ける）
```

### 4. memcached（s2 だけ）

- s2 で、現状を確認します（読むだけ。次の drop-in の `ExecStart` と突き合わせます）。

```bash
systemctl cat memcached.service
sudo ss -lntp | grep 11211
```

- `backup/s2/etc/systemd/system/memcached.service.d/listen.conf` です。
- `ExecStart` のパスと `-u` と `-m` は、上の出力に合わせます。`-l`（待ち受けの場所）だけ `0.0.0.0`（どの相手からでも受け付ける）にします。

```ini
[Service]
ExecStart=
ExecStart=/usr/bin/memcached -m 64 -p 11211 -u memcache -l 0.0.0.0
```

```bash
# 作業機
git pull --ff-only
mkdir -p backup/s2/etc/systemd/system/memcached.service.d
rm -rf backup/s2/etc/systemd/system/memcached.service.d/listen.conf
# 上の内容を配置する

git add -A && git commit -m "split: memcached を 0.0.0.0 で listen" && git push
```

- s2 で、反映します。

```bash
REPO=/home/isucon/private-isu-terraform
cd "$REPO" && git fetch origin
git switch feature/backup 2>/dev/null || git switch -c feature/backup
git pull --ff-only
sudo cp -a "$REPO/backup/s2/etc/systemd/system/memcached.service.d" /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl restart memcached.service

# 0.0.0.0:11211 であることを確認する。0.0.0.0 でないと他サーバからアクセスができない
sudo ss -lntp | grep 11211
```

期待出力（`0.0.0.0:11211` なら OK）:

```
[isucon@ip-10-42-0-181 ISUCON-2 ~/private-isu-terraform]$ sudo ss -lntp | grep 11211
LISTEN 0      1024         0.0.0.0:11211      0.0.0.0:*    users:(("memcached",pid=4543,fd=26))
```

- s1 から、s2 の memcached に届くことを確認します。

```bash
REPO=/home/isucon/private-isu-terraform
cd "$REPO" && git fetch origin
git switch feature/backup 2>/dev/null || git switch -c feature/backup
git pull --ff-only
source "$REPO/backup/common/ips.sh"  # MC_PRIV が s2 の IP

echo $MC_PRIV

# `STAT ...` が返れば OK。返らなければ s2 の listen.conf / restart を見直す
# netcatでCRLF終端のmemcachedコマンドを送る
printf 'stats\r\nquit\r\n' | nc -w 1 "$MC_PRIV" 11211 | head -3

# バージョンだけを見たいなら
printf 'version\r\nquit\r\n' | nc -w 1 "$MC_PRIV" 11211
```

- 続けて、memcached の向き先を env.sh に入れます。

- 作業機で、次を実行します。

```bash
git pull --ff-only
source backup/common/ips.sh

# ISUCONP_MEMCACHED_ADDRESS だけ足す（ISUCONP_DB_HOST は §3 のまま残す）
# 土台が空だと env.sh を空で上書きするので先に止める
if [ ! -s backup/s1/home/env.sh ]; then
  echo 'backup/s1/home/env.sh missing'
  exit 1
fi
for h in s1 s2; do
  grep -v '^ISUCONP_MEMCACHED_ADDRESS=' backup/s1/home/env.sh > /tmp/env.new
  echo "ISUCONP_MEMCACHED_ADDRESS=${MC_PRIV}:11211" >> /tmp/env.new
  cp /tmp/env.new backup/$h/home/env.sh
done

# ISUCONP_DB_HOST が s3、ISUCONP_MEMCACHED_ADDRESS が s2のIP:11211 であることを確認
cat backup/s1/home/env.sh
cat backup/s2/home/env.sh

git add -A && git commit -m "split: env.sh の memcached を s2 に向ける" && git push
```

- s1 と s2 で、反映します（自分の台の行だけ打つ）。

```bash
REPO=/home/isucon/private-isu-terraform
cd "$REPO" && git fetch origin
git switch feature/backup 2>/dev/null || git switch -c feature/backup
git pull --ff-only

## s1の場合はこちら
sudo cp -a "$REPO/backup/s1/home/env.sh" /home/isucon/env.sh
## s2の場合はこちら
sudo cp -a "$REPO/backup/s2/home/env.sh" /home/isucon/env.sh

# ★ restart（EnvironmentFile は起動時にしか読まれない）
sudo systemctl restart isu-python.service
sleep 4
systemctl is-active isu-python.service

# env がプロセスに載ったか確認する

```

- **`restart` を飛ばすと、env が効きません。**
- `EnvironmentFile` は、systemd が**サービス起動時に**読みます。
- ファイルを `cp` しただけでは、gunicorn のプロセスは古い値のままです。
- restart してから、プロセスの `/proc/<pid>/environ` を確認してください。

- アプリは、`ISUCONP_MEMCACHED_ADDRESS` が未設定だと `127.0.0.1:11211` を見ます。
- restart し忘れると、s1 の memcached を止めたときに **POST `/login` と `/register` が 500** になります。

```text
{"pass":false,"score":0,"success":0,"fail":8,
 "messages":["response code should be 200, got 500 (POST /login)",
             "response code should be 200, got 500 (POST /register)"]}
```

- restart 済みなら、s2 の memcached を見ます。
- restart が漏れたままでは、s1 のローカル memcached を見たままです。
- この時点のベンチは通っても、後で s1 の memcached を止めたときに 500 になります。

```bash
# 締めのベンチ（s1 で打つ）

TS=$(date +%Y%m%d%H%M%S)
if sudo test -f /var/log/nginx/access.log; then
  sudo mv /var/log/nginx/access.log /var/log/nginx/access.log.$TS
fi
sudo nginx -s reopen
sudo -iu isucon /home/isucon/private_isu/benchmarker/bin/benchmarker \
  -u /home/isucon/private_isu/benchmarker/userdata \
  -t http://localhost
echo "$(date -Iseconds)  score=  pass=  fail=  note=split-memcached" >> ~/bench-notes/scores.txt
```

実測サンプル（2026-10-13、memcached を s2（`0.0.0.0:11211`）に向けた時点）: `{"pass":true,"score":23735,"success":22277,"fail":0,"messages":[]}`（`fail=0`）。

- この時点のベンチは、通ります。
- 通らなければ、memcached の restart 状態を見ます。



### 5. s2 の gunicorn（HTTP :8080）

- **目的:** env.sh を載せます。
- 待ち受けの設定（listen）は、素体が `-b 0.0.0.0:8080` です。そのままで、s1 から届きます。
- ファイルは、触りません。

- s2 で、次を実行します。

```bash
systemctl cat isu-python.service
# ExecStart に -b 0.0.0.0:8080 があること。127.0.0.1 なら下の drop-in
sudo systemctl restart isu-python.service
curl -fsS -o /dev/null -m 5 "http://127.0.0.1:8080/" || \
  sudo journalctl -u isu-python.service -n 80 --no-pager
sudo ss -lntp | grep 8080   # 0.0.0.0:8080 であること
```


- `ExecStart` が `127.0.0.1:8080` のときだけ、作業機で drop-in を作ります。
- `systemctl cat` のパスとモジュールに、合わせます。

`backup/s2/etc/systemd/system/isu-python.service.d/bind.conf`:

```ini
[Service]
ExecStart=
ExecStart=/home/isucon/private_isu/webapp/python/.venv/bin/gunicorn app:app -b 0.0.0.0:8080 --log-file - --access-logfile -
```


### 6. s1 の gunicorn（unix socket）

- 作業機で、drop-in を作ります。
- `ExecStart=` の空行は、元の `-b 0.0.0.0:8080` を消すためのものです。忘れると、起動しません。

`backup/s1/etc/systemd/system/isu-python.service.d/unix.conf`:

```ini
[Service]
WorkingDirectory=/home/isucon/private_isu/webapp/python
ExecStart=
ExecStart=/home/isucon/private_isu/webapp/python/.venv/bin/gunicorn \
  --bind unix:/home/isucon/tmp/gunicorn.sock \
  --umask 007 \
  app:app
```

```bash
# 作業機
git pull --ff-only
mkdir -p backup/s1/etc/systemd/system/isu-python.service.d
# 上の内容を配置する

git add -A && git commit -m "split: s1 の gunicorn を unix socket に" && git push
```



- s1 で、反映します。

```bash

cd "$REPO" && git fetch origin
git switch feature/backup 2>/dev/null || git switch -c feature/backup
git pull --ff-only
source "$REPO/backup/common/ips.sh"

# 1. 現行。素体は -b 0.0.0.0:8080

# 3. ★ /home/isucon 以下の o+x（これが無いとソケットに到達できない）

sudo chmod -R a+rX /home/isucon/private_isu/webapp/public
ls -ld /home/isucon /home/isucon/private_isu /home/isucon/private_isu/webapp /home/isucon/tmp
# ソケットはisuconグループ・モード770。接続確認より先にnginxのグループを反映する
sudo usermod -aG isucon www-data

sudo cp -a "$REPO/backup/s1/etc/systemd/system/isu-python.service.d" /etc/systemd/system/

# 5. ソケットの残骸を消してから再起動する
#    restart だけだと古いソケットファイルが残って、新しい gunicorn が listen する前に
#    書き換わることがあり、`connect() failed (111: Connection refused)` になります
sudo systemctl stop isu-python.service

sudo systemctl start isu-python.service
sleep 4

# 6. 確認
# unix.conf が載っていること

# unix ソケットの listen 状態は ss -lxp で見る（ss -lntp には出ない）
sudo ss -lxp | grep gunicorn.sock && echo "LISTENING" || echo "NOT LISTENING"

# ここで何も表示されないことを確認します。表示される場合は 8080 が開いています
sudo ss -lntp | grep 8080 || echo "8080 closed (expected)"

# unix socket で応答することを確認します
# www-dataの権限で接続できることを確認する
sudo -u www-data python3 -c "
import socket
s = socket.socket(socket.AF_UNIX, socket.SOCK_STREAM)
s.settimeout(5)
s.connect('/home/isucon/tmp/gunicorn.sock')
s.close()
print('unix connect OK')
"
```

- **ソケットの権限だけでなく、親ディレクトリを辿れることも必要です。**
- nginx の www-data に通過権限が無いと、502 になります。
- gunicorn は isucon で動きます。isucon 所有のディレクトリを、gunicorn 側が辿れないことはありません。
- 起動に失敗したときは、journal も確認します。所有者・モード・unit の実効設定から、切り分けます。
- この検証では、次のエラーも出ました。

```text
gunicorn[3103]: connection to /home/isucon/tmp/gunicorn.sock failed:
 [Errno 1] Operation not permitted: '/home/isucon/tmp/gunicorn.sock'
gunicorn[3103]: Can't connect to /home/isucon/tmp/gunicorn.sock
systemd[1]: isu-python.service: Main process exited, code=exited, status=1/FAILURE
```

- nginx 側は、二次的な症状として `connect() failed (111: Connection refused)` を返します。
- **journalctl の方を見てください**（gunicorn 側が原因です）。

- この検証で、curl から出たメッセージは次のものでした。

```text
curl: (7) Failed to connect to localhost port 80 after 0 ms: Couldn't connect to server
```

- メッセージに `port 80` が出るだけでは、unix socket ではなく TCP へ接続した証拠にはなりません。
- 上の Python で、ソケットの接続権限を直接確認します。
- HTTP の応答は、§7 で nginx の向き先を反映してから確認します。

- ついでに、s1 の memcached を止めます。
- §4 の反映で、memcached=s2 を載せ終えました。§3 で一時的に起こした s1 の分は、もう要りません。

```bash
# s1 で
sudo systemctl stop memcached.service

# 何も出ないこと（s1 の 11211 は閉じる。s2 のは §4 で 0.0.0.0 のまま）
sudo ss -lntp | grep 11211 || true
```



- ソケットの実体は、**`isucon:isucon`、モード `770`** です（`--umask 007` が効きます）。

```text
srwxrwx--- 1 isucon isucon 0 /home/isucon/tmp/gunicorn.sock
```

- 親ディレクトリを `isucon:www-data 775` にしても、通常はソケット自体のグループは変わりません。
- この unit は、`User=isucon`・`Group=isucon` で動きます。
- root で一時的に chown する方法もあります。ただし再作成時に戻るため、手順には採用しません。

- この検証では、`--group www-data` を付けても、ソケットのグループは変わりませんでした。
- gunicorn のバージョンや起動権限で、挙動が変わります。一律には言えません。
- この手順では `Group=isucon` のままにします。www-data を isucon グループに入れて、接続を許可します。

```text
srwxrwx--- 1 isucon isucon 0 /home/isucon/tmp/gunicorn.sock   ← 変わらない
```

- nginx が 502 になる場合の対処は、**`www-data` を `isucon` グループに入れる**ことです。

```bash
sudo usermod -aG isucon www-data
id www-data
# uid=33(www-data) gid=33(www-data) groups=33(www-data),1002(isucon)

# 手順3で適用済み。再確認する場合もrestartでグループを確実に反映する
sudo nginx -t && sudo systemctl restart nginx
# gunicorn もソケットを作り直す
sudo systemctl restart isu-python.service
sleep 4

# nginx worker が isucon グループを持ったか確認する（/proc で見る）
for p in $(pgrep -u www-data nginx); do grep '^Groups' /proc/$p/status; done
# Groups:  33 1002    ← 1002 が isucon
```

反映後は 4 パスの `curl` で確認します（§7 の nginx 反映後）。

- unix 化直後は、ベンチを回しません。
- s1 の nginx は、まだ旧設定で 8080 を参照しているためです。
- ベンチは、§7 の nginx 反映の後に回します。

### 7. nginx（s1）— 静的 / 軽い unix / 重い HTTP

- **目的:** 素体は、全部 `proxy_pass http://localhost:8080;` です。
- s1 の 8080 は、もうありません。location（どの URL をどこに渡すかの指定）で分けます。

- **作るファイル:** `backup/s1/etc/nginx/conf.d/upstream.conf`（`upstream` 定義。つなぐ相手先の指定。http コンテキスト用）と、`backup/s1/etc/nginx/sites-enabled/isucon.conf`（server 定義）。
- 素体は短いので、**ファイル全体を置き換えてよい**です。

- `upstream` は、`server` ブロックの中に書けません（`nginx -t` が落ちます）。
- http 直下の、別ファイルに分けます。

- 作業機で、実施します。

`backup/s1/etc/nginx/conf.d/upstream.conf`（`${APP_PRIV}` は自分の値に置き換えます）:

```nginx

  server unix:/home/isucon/tmp/gunicorn.sock;
}

upstream heavy {
  server 10.42.0.181:8080;
}
```

`backup/s1/etc/nginx/sites-enabled/isucon.conf`:

```nginx
server {

  client_max_body_size 10m;

  location /css/ { }
  location /js/ { }

  }
  location = /register {
    proxy_set_header Host $host;

}
```

#### 1. nginx に `/image/` を足す（作業機で編集 → push → s1 で反映）

```nginx
  client_max_body_size 10m;

  location /js/ { }
```

#### 2. ファイルの配置と削除（作業機の staging を正にする）

- でかいバイナリ（画像など）は、git に載せません。
- 作業機の `staging/`（置き場所）を正とし、s1・s2 へは `rsync --delete` で配ります。
- **サーバで、直接 rm・編集しません。**
- 消したいファイルは、staging で消せば `--delete` で両台からも消えます。

```bash
# 作業機

source backup/common/ips.sh
mkdir -p staging/public
# staging/ は commit しない（git add -A の巻き添え防止）

# 初回だけ: s2 の現物を staging に持ってくる
rsync -a "isucon@${APP_PRIV}:/home/isucon/private_isu/webapp/public/" staging/public/

# 変更・削除は staging でやる
rm staging/public/js/old-bundle.js  # 例: 消したいファイルはここで消す

# s1（nginx 配信用）・s2（アプリ参照用）に反映。消した分も --delete で消える
for h in "$WEB_PRIV" "$APP_PRIV"; do
  rsync -a --delete staging/public/ "isucon@${h}:/home/isucon/private_isu/webapp/public/"
done
```


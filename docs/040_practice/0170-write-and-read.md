<a id="1-書き込みの-fsync-を-1-秒毎に"></a>

## 1. 書き込みの fsync を 1 秒毎に

[0160 §1](0160-memory-cache.md#1-仕事量を数える) の記録で、上位が `INSERT` 3 本＋`UPDATE`（合計 42 秒）でした。MySQL は既定では **書き込み 1 回ごとに記録をディスクへ書き切ります**（`innodb_flush_log_at_trx_commit = 1`）。これを **1 秒毎**に緩めます:

```ini
# s3: /etc/mysql/mysql.conf.d/97-isucon-flushlog.cnf
[mysqld]
innodb_flush_log_at_trx_commit = 2
```

MySQL とアプリ（s1・s2）を restart してベンチします。

```bash
# s3 で確認
sudo mysql -N -e 'SELECT @@global.innodb_flush_log_at_trx_commit'   # 2 であること
```

実測サンプル（2026-10-14、`c7a.xlarge` 2 台 + `c7a.large` 1 台 + ベンチマーカー `c7a.xlarge` / `ap-northeast-1`）: `score=367376` / `353018` / `356318`（3 本とも `fail=0`）。

点数は +2% 前後と小さめですが、**仕組み側を測ると効いています**（全件キャプチャの `R/Call`＝1 回あたりの時間）:

| クエリ | `= 1` のとき | `= 2` のとき | 変化 |
| --- | --- | --- | --- |
| `INSERT users` | 0.0060 秒 | **0.0031 秒** | -48% |
| `INSERT comments` | 0.0062 秒 | **0.0034 秒** | -45% |
| `UPDATE posts`（件数の列） | 0.0038 秒 | **0.0005 秒** | -87% |
| `INSERT posts`（画像つき） | 0.0231 秒 | 0.0202 秒 | -13%（転送分が支配的） |

小さい書き込みが半分以下になりました。**この手は残します。**

?> **注意点**: サーバが落ちたとき、直近 1 秒分の保存が失われ得ます。練習・検証では問題になりませんが、確実な保存が要る本番では `= 1` のままです。「点数のための緩め」として意図を記録しておきます。

### 観察すること

- 点数と、`R/Call`（1 回あたりの手間）の両方で判定します（[0015 §4](0015-sql-tuning.md#4-対象クエリを-1-本に決める) の「1 回が重いか」）
- 保存の確実さを下げている手であることを、残す変更に添えて記録します

<a id="2-読み込みの詳細をキャッシュする再挑戦"></a>

## 2. 読み込みの詳細をキャッシュする（再挑戦）

[0160 §3](0160-memory-cache.md#3-投稿詳細をキャッシュする) で一度は「戻した」詳細ページのキャッシュです。あの回の `fail` は、**上限無しのメモリ食い（OOM）**と、**nginx のファイル数の不足**という別の事故に絡んでいました。両方を直した状態（[0160](0160-memory-cache.md) の上限付きキャッシュ＋[0150 §8](0150-scale.md#8-トラブルシュート) の FD 上限）で、同じ手を**同じ条件で**再試行します。

```python
# get_posts_id(): 組み立て結果を id で保持（上限 128）
# post_comment(): その投稿だけ捨てる
# 初期化・ban: 全部捨てる
# 入れ口は _cache_put(limit) だけ。直接代入しない
```

3 本回して、`fail=0` が揃うかを見ます。

```bash
# ベンチマーカー専用機で打つ（3 本）
echo "$(date -Iseconds)  score=  pass=  fail=  note=cache2-post-128" >> ~/bench-notes/scores.txt
```

実測サンプル（2026-10-14）: `score=360357` / `358786` / `361234`（**3 本とも `fail=0`**）。

判定の材料は 2 つです:

- **`fail=0` が 3 本連続**（事故の再現なし。上限と FD を直してからは 8 本連続で `fail=0`）
- **ばらつきが小さく、基準群の上に乗った**（この手を入れていない 4 本: 352648 / 353018 / 356318 / 356107 に対し、3 本すべてがそれを上回る 358〜361 に収まった）

**この手は残します。**前回との違いは「事故の原因（OOM・FD）を先に潰してから測った」ことです。点数が同じでも、原因が残ったままの測定と、原因が無くなった測定では結論が違いました。

### 観察すること

- 一度戻した手を再試行するときは、**戻した原因が解消しているか**を先に確認します
- 3 本連続の `fail=0` を残す条件にします（1 本だけでは運かもしれません）

<a id="3-heavy-の振り分けを-5050-にする"></a>

## 3. heavy の振り分けを 50/50 にする

[0150](0150-scale.md) で `heavy` を s2 に寄せたのは、**当時 s1 が 2 vCPU で頭打ちだったから**です。s1 を `c7a.xlarge` にした今は逆転していて、ベンチ中の稼働（CPU の使用率）はこうなっていました（`mpstat 1 55` の平均）:

| 台 | 基準の稼働 | 見立て |
| --- | --- | --- |
| s1（`c7a.xlarge`） | 24% 稼働（`%idle 75.7`） | 空き |
| s2（`c7a.large`） | **62% 稼働**（`%idle 37.5`） | 運用側で最忙 |
| bench（`c7a.xlarge`） | 78% 稼働（`%idle 22.2`） | 負荷生成が上限気味 |

そこで `heavy` に s1 の gunicorn も加えます（nginx は既定の順番どおりに 50/50 で割り振ります）:

```nginx
# s1: /etc/nginx/conf.d/upstream.conf
upstream heavy {
  server unix:/home/isucon/tmp/gunicorn.sock;
  server 10.42.0.233:8080;
  keepalive 32;
}
```

```bash
sudo nginx -t && sudo systemctl reload nginx
```

振り分けが効いているかは、**確認用に**ログへ `$upstream_addr`（実際に流れた先）を一時的に出して見ます（このあと必ず元に戻します。[つまずいた点](#この節でつまずいた点) の 5）:

```bash
for i in $(seq 1 20); do curl -s -o /dev/null http://127.0.0.1/posts/1; done
# upstream: の内訳が 10:10 に割れていること
```

実測サンプル（2026-10-14、`c7a.xlarge` 2 台 + `c7a.large` 1 台 + ベンチマーカー `c7a.xlarge` / `ap-northeast-1`）: `score=351409` / `342950` / `345291`（3 本とも `fail=0`）。

**比べる相手は、近い時刻の基準です**（同じ 1 時間の幅の 3 本: `342517` / `343011` / `337940`、平均 341156）。手を入れた 3 本の平均は 346550 で **+1.6%**。効果は小さめですが、仕組みと整合しています（負荷が最忙の s2 から s1 へ移り、ベンチ中の s2 稼働が 62% → 38%、s1 が 24% → 44% に揃った）。**この手は残します。**

### 観察すること

- 50/50 が最適とは限りません。台のコア数が違うときは、稼働（`mpstat`）で狙いを確認します
- 割り当ての狙いは「最も稼働している台の頭を押さえる」ことです。点数より先に台の稼働が動きます

<a id="4-worker-数を増やす"></a>

## 4. worker 数を増やす

gunicorn の worker は、**1 プロセスで 1 リクエストずつ**受け持ちます。リクエストの多くが DB（s3）への往復待ちなので、CPU の数より多く並べても、待ちを重ねられます（[0070](0070-infra-params.md) で決めた 4 は「1 台に全部あった頃」の適正です）。s1・s2 の両方を 8 にします:

```bash
# 両台: -w 4 を含む drop-in を探して直す（複数あるので全部見る）
systemctl show -P DropInPaths isu-python.service
sudo sed -i 's/-w 4/-w 8/' <drop-in のファイル>
sudo systemctl daemon-reload && sudo systemctl restart isu-python.service
ps -o cmd -u isucon | grep gunicorn   # -w 8 になっていること
```

実測サンプル（2026-10-14、[§3](#3-heavy-の振り分けを-5050-にする) の状態の上）: `score=348334` / `349977` / `357325`（3 本とも `fail=0`）。

[§3](#3-heavy-の振り分けを-5050-にする) の 3 本（平均 346550）に対し +1.5%、基準（平均 341156）から積み上げで **+3.1%** です。効果はこれも小さめですが、`fail=0` が揃い、稼働の変化と整合しています。**この手も残します。**

締めの計測（同じ状態・計測付き）が `score=347372`（`fail=0`）です。ベンチ中の稼働は s1 `%idle 55.9` / s2 `%idle 62.0` / bench `%idle 20.3` でした。

### 観察すること

- worker を増やす前に、**その台の CPU に余裕があるか**を見ます（ここでは両台とも 40% 以上空いていました）
- 増やしすぎると 1 worker あたりのキャッシュ（ここではアプリ内キャッシュ）を薄めます。8 以上は再計測してからにします

<a id="6-トラブルシュート"></a>

## 6. トラブルシュート

### 点数が急に数 % 下がった（または上がった）— 何も変えていないのに

- **環境の移り変わり（ドリフト）**です。共有ホストの EC2 は時間帯や隣のテナントで性能が動きます（この章では 6 時間で 5% 動きました）
- 対処は「比べる相手を、近い時刻の基準に取り直す」ことです。絶対値の移り変わりに一喜一憂しないでください（[§5](#5-判定する)）
- 手の評価は **A（基準）→ B（手）を同じ幅で**測り直します。数時間前の基準と比べないでください

### `Too many open files`（nginx）

- 上げるのはプロセス側の FD 上限（同時に開けるファイルや接続の数）です。nginx は `worker_rlimit_nofile`（メインコンテキスト）＋ systemd の `LimitNOFILE`。[0150 §8](0150-scale.md#8-トラブルシュート) に手順があります
- 上げるのは**足りなくなっていることが分かってから**です（[0140 §5](0140-cut-remaining.md#5-ベンチマーカーの-fd-を見る) の流儀と同じ）

### キャッシュを入れたら `fail` が出た

- まず上限の有無を見ます（[0160 §3](0160-memory-cache.md#3-投稿詳細をキャッシュする)）
- 次に、その環境の他に壊れているもの（FD・メモリ）が無いかを見ます。**原因が残ったまま 1 つの手を評価しないでください**

### 点数の伸びが小さい手がある

- 効果が小さいことは結果です。仕組み（`R/Call` など）と整合していれば残す判断もあります（[§1](#1-書き込みの-fsync-を-1-秒毎に)）
- 整合しないときは「小さかった」と書いて、戻します

# 0110 複数台に分割する（最終: CPU / メモリを使い切る）

- [0110-split-3.md](0110-split-3.md) の続きです。
- 分ける作業が動く状態から、点数を分ける前の基準（[0110-split-1.md §6](0110-split-1.md#6-分割前のベースライン)）に戻します。そこから、超えます。
- この章が、このチュートリアルの最後です。

- 分けることで点数が下がる原因は、3 つです。
- この章は、3 つを 1 つずつ潰します。

| 原因 | 何が起きるか | 見る場所 |
| --- | --- | --- |
| 画像データの転送 | `/image` が s3 → s2 → s1 と毎回流れる | alp の `/image` の AVG と SUM(BODY) |
| 台をまたぐ通信の回数 | 1 リクエストに s1 → s2 → s3 の往復が入る | alp の全経路の AVG、`ss` の `:8080` / `:3306` |
| 台の偏り | 1 台だけ詰まり、他が余る | 各台の `mpstat 1` の `%idle`（CPU の空き） |

- 順番: 分割後の SQL を確認する（1.）→ 下がった理由を特定する（2.）→ 転送とホップを減らす（3.）→ worker 数で CPU を使い切る（4.）→ MySQL のメモリを使い切る（5.）→ upstream の負荷を均す（6.）→ 公式ベンチで判定する（7.）。
- 1 つずつ進めます。
- `fail`（エラーの件数）が 0 でない点数は、比べません。

- ベンチは、[0020-measure.md](0020-measure.md) の計測サイクルで回します。
- bench-prep（ベンチ前の準備）は、s1 で `mv` + `reopen`、s3 で slow log（遅い問い合わせの記録）の回転です。ベンチは s1 の `localhost` に打ちます。

## 1. 分割後の SQL を確認する

- 分けると、MySQL は s3 の台だけで動きます。
- 1 台に全部入った構成の DB にはあったけれど、s3 の DB に無いものがないか、まず確認します。

```bash
# s3 で打つ
sudo mysql -uisuconp -pisuconp isuconp -e "SHOW INDEX FROM comments;" 2>/dev/null
sudo mysql -uisuconp -pisuconp isuconp -e "SHOW INDEX FROM posts;" 2>/dev/null
```

```sql
USE isuconp;
SELECT COUNT(*) FROM information_schema.statistics
WHERE table_schema = 'isuconp'
  AND index_name IN ('idx_comments_post_created', 'idx_posts_user_created');
```

- 2 本あれば、次へ進みます。
- 無ければ、[0015-sql-tuning.md §6](0015-sql-tuning.md#6-インデックスを-1-本貼る) の `CREATE INDEX` を s3 で流します。

```sql
USE isuconp;
CREATE INDEX idx_comments_post_created ON comments (post_id, created_at);
CREATE INDEX idx_posts_user_created ON posts (user_id, created_at);
```

- 貼ったら、同じ `EXPLAIN` で `key` が変わったことを確認します。それから、ベンチします。

```sql
EXPLAIN
SELECT * FROM comments WHERE post_id = 1 ORDER BY created_at DESC LIMIT 3;
```

?> 索引を 1 本ずつ貼り直す代わりに、1 台構成の DB を丸ごと移すこともできます（`mysqldump` で s1 → s3。データと索引が、そのまま移ります）。どちらでも、移したあとの `SHOW INDEX` で 2 本あることを確認します。

- N+1（同じ問い合わせの繰り返し）の解消は、アプリのソースです。
- `backup/s1` に積んでいれば、s1 には残っています。ただし増やした s2 の `app.py` は、素体（配布された元の状態）のままです。
- 残っていない場合は、[0015-sql-tuning.md §7](0015-sql-tuning.md#7-n1-を一括化する) の差分を `backup/s1/home/private_isu/webapp/python/app.py` と s2 側の同じファイルに入れます（[0110-split-2.md §3](0110-split-2.md#3-アプリの-envshs1-と-s2同じ内容) の注と同じです）。

- 1 台構成で振った DB の設定ノブ（`backup/s1/etc/mysql/` の drop-in＝設定の追加ファイル）は、s3 に移してあることを確認します（[0110-split-2.md §2](0110-split-2.md#2-mysqls3-だけ) の注どおり）。

```bash
# s3 で打つ
ls -l /etc/mysql/mysql.conf.d/
sudo mysql -N -e 'SELECT @@innodb_flush_log_at_trx_commit'
```

- 計測は、[0020-measure.md](0020-measure.md) の計測サイクルで回します。
- `slp my` の合計時間の並べ替えの基準は、**`sum-query-time`** です。
- 既定は件数の昇順です。`head` だけでは、時間の上位を選べません。

実測サンプル（2026-10-13。s3 は素体の DB で索引が PRIMARY のみだったため 2 本を貼り直した）: `EXPLAIN` は `type: ref` / `key: idx_comments_post_created` / `rows: 12`（`Backward index scan`）になりました。**この索引 2 本だけで `score=25439`（`fail=0`）**となり、分けた直後の 10909 から +14530 です。

### 観察すること

- s3 の `SHOW INDEX` に [0015-sql-tuning.md](0015-sql-tuning.md) で入れた 2 本があること
- `EXPLAIN` で `type: ref` / `rows` が LIMIT に近いこと
- slp で `comments` の問い合わせが上位で、`examined`（読んだ行数）が `sent`（返した行数）に近いこと

## 2. 下がった理由を特定する

- 直す前に、3 つの原因のどれが主かを数字で決めます。
- 決めずに worker を増やすと、詰まっている台以外を増やすことになります。

### 分割前後の alp を比べる

```bash
# s1 で打つ（bench-prep のあと）
MATCH='/posts/[0-9]+,/image/[0-9]+,/@[a-zA-Z0-9_]+'
sudo cat /var/log/nginx/access.log | alp ltsv --sort sum --reverse -m "$MATCH" | head -12
```

- 分ける前（[0110-split-1.md §6](0110-split-1.md#6-分割前のベースライン) の記録）と比べます。
- `/image` の AVG と SUM(BODY) が、跳ねたかを見ます。
- 跳ねていれば、**画像データの転送**が主です（[§3](#3-転送とホップを減らす) へ）。

### 台ごとの稼働をベンチ中に取る

- 各台で、ベンチを回しているあいだの別 SSM セッションから打ちます。
- プロファイラ（計測用の道具）の併用と同様に、観測のための計測です。点数は分けます。

```bash
# 各台で打つ（ベンチ中に 5 秒だけ）
mpstat 1 5
free -h
ss -s | head -5
```

- s2 だけ `%idle` が 0 に近く、s1・s3 が余っている → **台の偏り**です（[§6](#6-upstream-の負荷を均す) へ）
- 3 台とも `%idle` が 0 に近いのに点数が低い → **台をまたぐ通信**が主です（[§3](#3-転送とホップを減らす) へ）
- `free -h` の `available`（使えるメモリ）が枯れている台がある → その台のメモリ配分を見ます（[§5](#5-mysql-のメモリを使い切るs3) へ）

実測サンプル（2026-10-13、`mpstat 1 5` のベンチ中平均 `%idle`）:

| 台 | §2 の時点（score 25439） | §7 最終の時点（score 96265） |
| --- | --- | --- |
| s1（nginx + unix） | 85.1 | 39.0 |
| s2（heavy） | 81.9 | 71.6 |
| s3（MySQL） | 61.8 | **4.0** |

- §2 の時点は、3 台とも CPU が余っていました。`%idle` が 0 に近くありません。
- そのため、**詰まりは CPU ではなく通信の待ち（遅延）**と判定しました（[§3](#3-転送とホップを減らす) と worker 増が効きます）。
- 最終では、s3 の MySQL が `%idle` 4% と頭打ちになりました。これが、次の上限です。

### 観察すること

- 「画像の転送 / 台をまたぐ通信 / 台の偏り」のどれが主かを、alp と `mpstat` の 2 つで言えること
- 主でない原因を先に直していないこと（1 つずつです）

## 3. 転送とホップを減らす

- ホップは、台をまたぐ通信 1 回のことです。リクエスト 1 つに s1 → s2 → s3 のホップが 2 回入ります。
- 0030〜0100 で 1 台構成として入れた設定は、[0110-split-2.md §7](0110-split-2.md#7-nginxs1--静的--軽い-unix--重い-http) の site conf の置き換えで消えています。
- ここでは、転送とホップの回数に効くものだけ、1 つずつ入れ直します。

### 3-a. `/image` を s1 の nginx でキャッシュする

- `/image` は、s3 → s2 → s1 と流れる画像データです。
- s1 の nginx が一度覚えると、以降はその転送が消えます（[0030-cache.md §5](0030-cache.md#5-nginx-で-1-箇所だけキャッシュして-hit-率で評価する) と同じ 1 つです）。

`backup/s1/etc/nginx/conf.d/cache-image.conf`:

```nginx
proxy_cache_path /var/cache/nginx/image levels=1:2 keys_zone=image:10m max_size=1g inactive=60m use_temp_path=off;
```

- `backup/s1/etc/nginx/sites-enabled/isucon.conf` の `location /`（heavy へ流す場所）から、`/image` だけ分けてキャッシュします。

```nginx
location /image/ {
  proxy_set_header Host $host;
  proxy_pass http://heavy;
  proxy_cache image;
  proxy_cache_valid 200 60s;
  proxy_cache_key "$request_method$host$request_uri";
  proxy_cache_methods GET HEAD;
  proxy_no_cache $cookie_session $http_authorization;
  proxy_cache_bypass $cookie_session $http_authorization;
  add_header X-Cache $upstream_cache_status always;
}
```

```bash
# 作業機
git pull --ff-only
mkdir -p backup/s1/etc/nginx/conf.d
# 上の 2 つの内容を各ファイルに配置する
git add -A && git commit -m "split4: /image を s1 の nginx でキャッシュ" && git push
```

```bash
# s1 で反映
git pull --ff-only
SOURCE=backup/s1/etc/nginx/sites-enabled/isucon.conf
test ! -L "$SOURCE" || SOURCE=backup/s1/etc/nginx/sites-available/isucon.conf
TARGET=$(readlink -f /etc/nginx/sites-enabled/isucon.conf)
test -s backup/s1/etc/nginx/conf.d/cache-image.conf && test -n "$TARGET" || exit 1
sudo cp -a backup/s1/etc/nginx/conf.d/cache-image.conf /etc/nginx/conf.d/
sudo cp -a "$SOURCE" "$TARGET"
sudo mkdir -p /var/cache/nginx/image
sudo chown www-data:www-data /var/cache/nginx/image
sudo nginx -t && sudo systemctl reload nginx
curl -sI http://127.0.0.1/image/1.jpg | grep -i 'x-cache'
curl -sI http://127.0.0.1/image/1.jpg | grep -i 'x-cache'
# 1 回目 MISS、2 回目 HIT が見えること
```

- bench-prep → 公式ベンチ 1 本 → `scores.txt` に 1 行、の順で回します。
- ベンチ後に、HIT 率と alp を見ます。

```bash
# s1 で打つ（ベンチ後）
sudo cat /var/log/nginx/access.log | grep '/image' | grep -o 'cache:[A-Z-]*' | sort | uniq -c | sort -nr
MATCH='/posts/[0-9]+,/image/[0-9]+,/@[a-zA-Z0-9_]+'
sudo cat /var/log/nginx/access.log | alp ltsv --sort sum --reverse -m "$MATCH" | head -12
echo "$(date -Iseconds)  score=  pass=  fail=  nginx_hit=  note=split4-image-cache" >> ~/bench-notes/scores.txt
```

実測サンプル（2026-10-13。[0080-app-tuning.md §2](0080-app-tuning.md#2-アップロード画像を静的ファイルにする投稿の本体データは-db-に残す) で `/image` は s1 のファイル配信済みのため、手順書の注記どおり DB フォールバックの `@app` 側に `proxy_cache` を入れた形）: `{"pass":true,"score":31974,"success":30613,"fail":0,"messages":[]}`（§2 時点の 25439 から +6535。ベンチ後の cache 分布は `HIT` 6098 / `MISS` 134 / `BYPASS` 722 / ファイル直返し `cache:-` 14418 でした）。

- `proxy_cache` は写しです。投稿の本体データは s3 の MySQL にあります。消しません（[0030-cache.md §1](0030-cache.md#1-投稿の本体データは-mysql-と-ebs)）
- `/image` をファイル化（[0080-app-tuning.md §2](0080-app-tuning.md#2-アップロード画像を静的ファイルにする投稿の本体データは-db-に残す)）していれば、そのファイルを s1 に置いて nginx が直接返す形が先です。キャッシュより 1 段減ります

### 3-b. upstream を使い回す（keepalive 32）

- s1 → s2 は、台をまたぎます。毎リクエストの接続の張り直しが、そのままコストになります（[0040-http-client.md §4](0040-http-client.md#4-nginx-の-upstream-を使い回す1-台でも効く) と同じ 1 つです）。

- `backup/s1/etc/nginx/conf.d/upstream.conf` に `keepalive`（接続の使い回し）を足します。
- `heavy` へ向ける location に、2 行を足します（light の unix socket は対象外です）。

```nginx
upstream light {
  server unix:/home/isucon/tmp/gunicorn.sock;
}

upstream heavy {
  server 10.42.0.181:8080;
  keepalive 32;
}
```

```nginx
# heavy へ向ける location（`location /` と `location /image/`）に足す 2 行
proxy_http_version 1.1;
proxy_set_header Connection "";
```

```bash
# 作業機
git pull --ff-only
# 上の内容を upstream.conf と site conf に反映する
git add -A && git commit -m "split4: heavy の upstream に keepalive" && git push
```

```bash
# s1 で反映
git pull --ff-only
SOURCE=backup/s1/etc/nginx/sites-enabled/isucon.conf
test ! -L "$SOURCE" || SOURCE=backup/s1/etc/nginx/sites-available/isucon.conf
TARGET=$(readlink -f /etc/nginx/sites-enabled/isucon.conf)
test -s backup/s1/etc/nginx/conf.d/upstream.conf && test -n "$TARGET" || exit 1
sudo cp -a backup/s1/etc/nginx/conf.d/upstream.conf /etc/nginx/conf.d/upstream.conf
sudo cp -a "$SOURCE" "$TARGET"
sudo nginx -t && sudo systemctl reload nginx
curl -fsS -o /dev/null -m 5 http://127.0.0.1/
curl -fsS -o /dev/null -m 5 http://127.0.0.1/image/1.jpg
```

- bench-prep → 公式ベンチ 1 本 → `scores.txt` に 1 行、の順で回します。
- 効いている証拠は、`:8080` への `established`（つながったままの接続）が残ることです。

```bash
# s1 で打つ（ベンチ直後）
ss -Htan state established | grep ':8080' | wc -l
ss -Htan state time-wait | wc -l
echo "$(date -Iseconds)  score=  pass=  fail=  note=split4-keepalive-32" >> ~/bench-notes/scores.txt
```

実測サンプル（2026-10-13）: `{"pass":true,"score":32234,"success":30877,"fail":0,"messages":[]}`（31974 から +260、`fail=0`。ベンチ直後の `ss -Htan state established | grep ':8080'` は 3503 本と残り、使い回しが効いていました）。

### 3-c. 静的と画像に `expires` を入れ直す

- site conf を置き換えたので、消えています。
- [0060-static-cache.md §4](0060-static-cache.md#4-expires-で保持期間を付ける1-箇所だけ) と同じ 1 行を、対象 location に 1 箇所だけ入れます（例: `location /css/` に `expires 1d;`）。
- 1 箇所ずつ、bench-prep → 公式ベンチ → `scores.txt` の順で回します。

実測サンプル（2026-10-13、`location /css/` に `expires 1d;` の 1 箇所）: `score=32135`（`pass=true` / `fail=0`。32234 から -99 でノイズ内。ベンチマーカーはブラウザの記憶（キャッシュ）を再現しないため点数は動かなくてよい）。

### 観察すること

- `/image` の AVG と SUM(BODY) が落ちました（3-a）。HIT だけ増えて AVG が落ちないなら測る場所がずれています
- `established :8080` が張り付きます（3-b）。ベンチ後に 0 本なら使い回しが効いていません
- `fail` が 0 です。ログイン中の応答をキャッシュして `fail` が出たら `proxy_no_cache` を広げます（覚える時間を延ばしません）

## 4. worker 数で CPU を使い切る

- 転送が減ったら、次は各台の 2 コアを使い切ります。
- 足すのは、gunicorn の worker（同時に受け持つ処理）だけです。
- 1 つずつ、台を 1 つに絞って変えます。

### s2（heavy）の gunicorn worker

- [0070-infra-params.md §5](0070-infra-params.md#5-gunicorn-の-worker-プロセス数少なすぎも多すぎも遅い) の drop-in を、s2 に置きます。
- `-b 0.0.0.0:8080` のままにします。値は、小さい方から（2 → 4）。

`backup/s2/etc/systemd/system/isu-python.service.d/workers.conf`:

```ini
[Service]
ExecStart=
ExecStart=/home/isucon/private_isu/webapp/python/.venv/bin/gunicorn app:app -b 0.0.0.0:8080 -w 4 --log-file - --access-logfile -
```

```bash
# 作業機
git pull --ff-only
mkdir -p backup/s2/etc/systemd/system/isu-python.service.d
# 上の内容を配置する
git add -A && git commit -m "split4: s2 の worker を 4 に" && git push
```

```bash
# s2 で反映
cd /home/isucon/private-isu-terraform && git pull --ff-only
test -s backup/s2/etc/systemd/system/isu-python.service.d/workers.conf || exit 1
sudo cp -a backup/s2/etc/systemd/system/isu-python.service.d/workers.conf /etc/systemd/system/isu-python.service.d/
sudo systemctl daemon-reload
sudo systemctl restart isu-python.service
ps -ef | grep gunicorn | grep -v grep | head -10
curl -fsS -o /dev/null -m 5 http://127.0.0.1:8080/login
```

- bench-prep（s1）→ 公式ベンチ 1 本 → `scores.txt` に 1 行、の順で回します。
- ベンチ中に s2 で `mpstat 1 5` を回し、`%idle` が減ったかを見ます。

実測サンプル（2026-10-13、s2 の worker を 2 → 4）: `score=53827` と再現の `score=54833`（いずれも `-w 2`、`fail=0`）→ **`score=76693`**（`-w 4`、`fail=0`）。32135 から worker 増だけで +21692 → +44558 と最大の 1 つでした（順番待ちを受ける worker は、DB の応答待ちに時間を使うので、数を増やすと並列にさばけます）。

### s1（light）の gunicorn worker と nginx

- 同じ流儀で、s1 の gunicorn を増やします。
- 待ち受けの設定（bind）は、unix socket のままにします。`ExecStart` は [0110-split-2.md §6](0110-split-2.md#6-s1-の-gunicornunix-socket) の形に合わせます。
- nginx は、`worker_processes auto;` なら CPU の数に合わせてあります。増やすのは、gunicorn からです。

実測サンプル（2026-10-13、s1 の unix gunicorn を `-w 4` に）: `score=77767`（`pass=true` / `fail=0`。76693 から +1074。s1 の軽い経路は詰まっていなかったため効果は小さめです）。

### DB 接続数とセットで見る

- worker を増やすと、s3 への接続が増えます。
- s3 で、見るだけです。

```bash
# s3 で打つ（ベンチ中に）
sudo mysql -N -e "SHOW STATUS LIKE 'Threads_connected'; SHOW VARIABLES LIKE 'max_connections';"
```

- `too many connections` が出たら、`max_connections` を先に上げません。worker を 1 つ戻します（[§5](#5-mysql-のメモリを使い切るs3) の `max_connections` は、そこで振ります）。

### 観察すること

- worker 数と点数 / `oha`（簡易的な負荷検査ツール）の p99 の対応表を言えます（2 → 4 の 2 点があれば十分です）
- ベンチ中の s2 の `%idle` が減りました。減らないのに点数が動かないなら、s2 は詰まっていません（[§6](#6-upstream-の負荷を均す) へ）
- worker 毎のメモリ使用量（RSS）× N が `free -h` の `available` を超えていません

## 5. MySQL のメモリを使い切る（s3）

- s3 は、MySQL 専用です。
- 1 台構成では、アプリとメモリを分け合っていました。`innodb_buffer_pool_size`（検索結果を覚えておく場所の大きさ）を最初の調整項目にしませんでした。
- 複数台では、振れます。4GiB の 60〜70%（2.5〜3G）から始めます。

`backup/s3/etc/mysql/mysql.conf.d/99-isucon-bufferpool.cnf`:

```ini
[mysqld]
innodb_buffer_pool_size = 2560M
```

```bash
# 作業機
git pull --ff-only
mkdir -p backup/s3/etc/mysql/mysql.conf.d
# 上の内容を配置する
git add -A && git commit -m "split4: buffer pool を 2560M に" && git push
```

```bash

sudo cp -a "$REPO/backup/s3/etc/mysql/mysql.conf.d/99-isucon-bufferpool.cnf" /etc/mysql/mysql.conf.d/
sudo systemctl restart mysql
sudo mysql -N -e 'SELECT @@innodb_buffer_pool_size'
free -h
```

- **mysqld を restart したら、s1・s2 のアプリも restart します。**
- 古い接続のままだと、`fail` します。

```bash
# s1 と s2 で打つ
sudo systemctl restart isu-python.service
systemctl is-active isu-python.service
```

- bench-prep → 公式ベンチ 1 本 → `scores.txt` に 1 行、の順で回します。
- 効きは、ヒット率（覚えていたデータが使われた割合）で見ます。

```bash
# s3 で打つ
sudo mysql -N -e "SHOW ENGINE INNODB STATUS\G" | grep -A3 'Buffer pool hit rate'

echo "$(date -Iseconds)  score=  pass=  fail=  note=split4-bufferpool-2560M" >> ~/bench-notes/scores.txt
```

実測サンプル（2026-10-13）: `{"pass":true,"score":76916,"success":72568,"fail":0,"messages":[]}`（77767 から -851 でノイズ内。データが小さく既にメモリに載っていたため、点数より `free -h` の `available`（s3 で 2.0Gi）とヒット率を見る手です）。

- ヒット率が上がらない・`free -h` の `available` が枯れる → 値を 1 つ戻します
- `max_connections`（接続の上限）は [§4](#4-worker-数で-cpu-を使い切る) の worker 合計より上にします。ここでも 1 つだけです（`SHOW VARIABLES LIKE 'max_connections'` で見る → 必要なら上げる → ベンチ）
- mysqld が起動しなくなったら drop-in を外して restart します（[0010-setup.md](../010_common/0010-setup.md#mysqld-が起きないslow-設定の直後) の「mysqld が起きない」と同じです）

### 観察すること

- `@@innodb_buffer_pool_size` が指定どおりで、`free -h` の `available` に余裕があります
- ベンチの点数とヒット率をセットで言えます（点数だけ見ません）
- s1・s2 のアプリを restart しています（省略すると `fail` が出ます）

## 6. upstream の負荷を均す

- ここまでで転送と通信の回数が減り、worker が増えていたら、詰まる台と余る台がはっきり見えているはずです。
- ベンチ中に各台で `mpstat 1 5` を取り、`%idle` が揃うように振り分けます。

```bash
# 各台で打つ（ベンチ中）
mpstat 1 5
```

- 変えるのは、site conf の振り分け 1 箇所だけです。
- 例として、重い経路（`location /`）を s2 だけでなく s1 の unix socket にも回します。
- `upstream heavy` に s1 を 1 行足します。重みで、割合を変えます。

```nginx
upstream heavy {
  server unix:/home/isucon/tmp/gunicorn.sock weight=1;
  server 10.42.0.181:8080 weight=2;
  keepalive 32;
}
```

- `weight` は台の処理能力に比例させます。同じ型なら `1:1` から始めます
- s1 は nginx も動くので、s2 より軽めに見ます（`1:2` など）
- 振り分けを変えたら、必ず bench-prep → 公式ベンチ 1 本です。2 箇所以上を同時に変えません
- s2 に集まりすぎる場合は、重い location の一部（例: `location /posts/`）を light 側に移すのも 1 つです。どちらも「台の `%idle` が揃うか」で決めます

実測サンプル（2026-10-13、`upstream heavy` に s1 の unix socket を `weight=1`、s2 を `weight=2` で追加）: `{"pass":true,"score":95999,"success":91304,"fail":0,"messages":[]}`（76916 から **+19083**、`fail=0`。振り分けで同時にさばける数が増えた効果が 2 番目に大きい手でした）。

### 観察すること

- 3 台の `%idle` がベンチ中に揃って減ります（1 台だけ 0 で他が余る状態が解消しています）
- 振り分けの前後で点数を言えます。`fail` が 0 です
- CPU が使い切れても点数が増えないなら、次は通信の回数（[§3](#3-転送とホップを減らす)）に戻ります

```bash
# s1 で打つ
sudo -iu isucon /home/isucon/private_isu/benchmarker/bin/benchmarker \
  -u /home/isucon/private_isu/benchmarker/userdata \

echo "$(date -Iseconds)  score=  pass=  fail=  note=split4-final" >> ~/bench-notes/scores.txt
```

実測サンプル（2026-10-13）: `{"pass":true,"score":96265,"success":91576,"fail":0,"messages":[]}`（`fail=0`。分ける前の基準 50920 を **+45345** で超えました）。

## 残す変更は台ごとの backup に積む

- ここからは複数台です。変更は、台ごとの `backup/s1`・`s2`・`s3` に積みます（[0110-split-1.md §3](0110-split-1.md#3-分割前のバックアップ) の形です）。
- 戻すときは、逆に `cp` で戻します。

## 8. トラブルシュート

### `/image` の HIT が増えない

- `X-Cache` が `MISS` のままならキーか `proxy_no_cache` の範囲を見ます（[0030-cache.md §7](0030-cache.md#7-トラブルシュート)）
- ファイル化（0080-app-tuning.md §2）したのにキャッシュしているなら、ファイル配信（0060-static-cache.md §3）の方が 1 段減ります

### keepalive を入れたら 502 / fail

- `upstream` の名前と `proxy_pass` がずれています。`nginx -t` を先に見ます（[0040-http-client.md §8](0040-http-client.md#8-トラブルシュート)）
- `proxy_http_version 1.1` と `proxy_set_header Connection ""` は location の内側です

### worker を増やしたら fail が増える

- s3 の `max_connections` を疑います。`too many connections` なら worker を戻します（§5 で `max_connections` を振ります）
- `too many open files` なら FD（同時に開けるファイルや接続の数）の上限です（[0070-infra-params.md §6](0070-infra-params.md#6-ファイルディスクリプタの上限数足りないときだけ効く)）

### buffer pool を増やしたら mysqld が起きない

- `free -h` の `available` を超えています。drop-in を外して restart します（[0010-setup.md](../010_common/0010-setup.md#mysqld-が起きないslow-設定の直後) の「mysqld が起きない」と同じです）
- 戻したら s1・s2 のアプリも restart します

- 0110 まで終わったら、[0120-db-load.md](0120-db-load.md)（DB の仕事量）→ [0130-response-build.md](0130-response-build.md)（レスポンス生成）に進みます。
- 全部終わったら、終盤作業（[0030-ops.md](../010_common/0030-ops.md) の「ログを止める（終盤）」「終盤チェック（17:00 以降）」）に進みます。
